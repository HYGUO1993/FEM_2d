# FemLab Studio → Civil Agent 平台：LLM 战略路线图

> 目标：不满足于"结构力学 ChatBot"，把 LLM + Agent 能力推广到土木工程的方方面面，
> 最终形成「确定性求解内核 + 垂直知识引擎 + 专属小模型」的领域智能平台。
> 本文基于 v0.3.1 迭代中实际踩坑的一手经验，提出务实的分阶段路径。

---

## 一、核心判断：土木领域的 LLM 不是"生成答案"，而是"编排确定性求解器"

这是全文最重要的一个观点，也是从本次迭代反复验证出来的：

- 结构力学有**精确数学**（刚度法、影响线、屈曲特征值）——算得对是必须的，**不能靠 LLM 猜**。
- 规范有**确定性条文**（荷载组合、构造要求、截面验算）——需要精确引用，**不能靠 LLM 记忆**。
- 工程是**安全攸关**的——错一个数字可能出事故，这与"生成式应用允许幻觉"完全对立。

因此正确的分工是：

```
LLM（推理/意图/编排/解读）  ──调用──►  确定性内核（计算/校验/检索）
   ↑  只做：理解需求、拆解任务、              ↑  只做：求解、验算、查规范、
   │       选择工具、解释结果、                  │       生成图纸/表格、比对条文
   │       自然语言交互                          │       （永远正确，可溯源）
```

**LLM 永不直接产出不可验证的数字。** 这正是本次"独立参考求解器兜底 LLM 结果"模式的推广。

## 二、本次迭代已经踩过的垂直 agent 痛点（一手证据）

| 痛点 | 现象（本次实测） | 解法 |
|---|---|---|
| **长结构化 JSON 生成不可靠** | 5x5 框架 8 轮全卡校验；3x3 也失败过 | 细分工具 / DSL / 程序化生成器（不让 LLM 手写 36 节点 JSON） |
| **跨语言/跨层序列化缝隙** | Rust `ChatMessage` 丢 `tool_call_id` → 400 | harness 层 schema 契约 + 自动化测试 |
| **工具粒度太粗** | `apply_model` 整模型覆盖，错误不收敛 | 细粒度工具：add_node/add_beam/set_load… |
| **数值不可信** | agent 反复"重新求解确认结果" | 结果全部走求解器，LLM 只解读 |
| **上下文膨胀** | 模型 JSON 在多轮中重复 3~4 次 | 摘要工具（已有雏形）+ 分层记忆 |
| **失败不收敛** | 校验失败 → 全量重生成 → 再失败 | 校验反馈 + 增量修改（而非重来） |

**结论**：这些痛点都不是"换个更强的模型"能解决的，而是**架构问题**——需要把 LLM 从"生成者"重构为"编排者"。

## 三、分层演进路线（ChatBot → 专属 Agent 平台）

### L1 — ChatBot（v0.3.0 已达成）
问答式交互，LLM 直接输出 JSON 模型。

### L2 — Tool-Agent 闭环（v0.3.1 已达成雏形）
建模-校验-求解-解读 工具循环。已验证：工具调用链路、容错解析、结果摘要。

### L3 — 编排型 Agent（下一阶段核心）
- **工作流编排**：把"建模→分析→设计→出报告"变成显式状态机，而非自由循环
- **约束校验层**：schema 校验（已有）+ 物理约束（平衡、机构判定）+ 规范约束
- **增量修改**：细分工具 + 差异式编辑，失败时局部修而非重来
- **规范 RAG**：结构化规范库（GB 50010/50017、AISC、Eurocode），条文级检索 + 引用溯源

### L4 — 垂直知识引擎
- **规范条文库**：条文切片 + 表格结构化 + 公式可执行化（公式不再是文本，而是可调用函数）
- **工程案例库**：历史模型+结果，few-shot 检索增强
- **图计算**：模型 → 依赖图 → 自动生成传力路径、冗余度、灵敏度分析

### L5 — 专属小模型 + 混合路由
- **子任务微调**：荷载识别、截面选择、规范分类、错误诊断——这些**小、边界清晰、数据可得**的任务用 7B-14B 开源模型（Qwen2.5 等）蒸馏大模型输出，微调成本可控
- **混合路由**：简单/高频任务 → 小模型（快、便宜、可控）；复杂推理 → 大模型
- **不训练通用大模型**：训练 LLM 是重资产，先把工具生态和数据闭环做起来

### L6 — 多 Agent 协作
- 建模 agent / 审图 agent / 验算 agent / 造价 agent / 规范 agent 分工协作
- 每个 agent 绑定专属工具集 + 专属知识库 + 专属校验器

## 四、土木"方方面面"横向扩展地图（按落地难度排序）

| 领域 | 确定性内核 | LLM 角色 | 难度 |
|---|---|---|---|
| 结构分析（已有） | FEM 求解器 | 建模/解读 | ✅ 已落地 |
| 结构设计 | 截面验算、配筋、规范校核 | 选截面、生成计算书 | ★★ |
| 荷载与规范 | 荷载组合器、规范条文库 | 条文检索、组合生成 | ★★ |
| 施工验算 | 脚手架/模板/临时结构计算 | 方案生成、工况分析 | ★★★ |
| 造价/工程量 | 算量引擎（从模型提取） | 清单生成、询价 | ★★ |
| 检测与鉴定 | 既有结构评估、加固设计 | 报告解读、方案建议 | ★★★ |
| 教学（近水楼台） | 已有求解器 | 出题、判分、交互实验、个性化讲解 | ★（最先做） |
| BIM/GIS 接口 | IFC/DXF 解析 | 模型理解、语义映射 | ★★★ |

**建议扩张顺序**：教学 → 结构设计（配筋/截面验算）→ 荷载规范 RAG → 造价算量 → 施工/鉴定。

## 五、让"专属 agent 克服垂直痛点"的落地抓手（本次可直接复用）

1. **确定性内核服务化**：把 femcli 从"spawn 子进程"升级为**常驻服务/REST/WASM**（HANDOFF 已列方向），
   成为所有上层 agent 的"手"——这是 L3 的地基，先做这个。
2. **把校验器做成独立层**：schema + 物理 + 规范三层校验，LLM 输出必须过校验才落地。
3. **领域 DSL**：设计一种结构描述语言（如 `frame(5x5, span=3m, story=3m, load=10kN)`），
   LLM 生成 DSL → 确定性解析成模型——比生成 JSON 可靠一个数量级。
4. **数据飞轮**：用户真实操作日志（建模/改参/纠错）→ 清洗 → 对齐数据 → 微调小模型。
5. **结果解读 + 理论对照**：自动对比 qL²/8、5qL⁴/384EI 等理论公式（Agent Phase 2），
   这是"让 LLM 发挥到极致"的示范——LLM 擅长解释"为什么"，求解器保证"是什么"。

## 六、推荐的下一步（3 个月内可落地，优先级排序）

1. **确定性内核服务化**（femcli 常驻 + 可编程 API）——所有 agent 的地基
2. **细分工具 + 领域 DSL**——解决"长 JSON 生成不可靠"这一最痛的点
3. **结果自动解读 + 理论对照**——教学价值立现，LLM 价值最直观
4. **规范 RAG 原型**（先做一个小领域，如混凝土梁配筋 GB 50010）——验证垂直知识引擎可行
5. **教学出题/判分 agent**——低风险、高频、易扩散的起点

---

## 七、风险与务实提醒

- **不要急着训模型**：先跑通"工具生态 + 数据闭环"，数据比模型稀缺。
- **确定性内核永远是第一优先级**：LLM 可以换（DeepSeek/Qwen/GPT/Claude 都行），
  求解器和校验器是护城河。
- **规范数据合规**：商用需授权规范文本；教学可用公开条文 + 教材案例起步。
- **安全边界**：任何"设计/验算"输出必须强制带规范条款溯源 + 免责声明，LLM 结果仅供参考。
