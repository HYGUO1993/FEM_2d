# LLM 建模助手智能化方案（讨论稿）

> 目标：把当前「自然语言 → 单次 JSON 模型」的助手，升级为结构力学教学场景下的智能建模教练。
> 本文为方案设计，未实现。

## 现状与问题

| 现状 | 问题 |
|---|---|
| 单轮对话：描述 → 返回模型 JSON → 应用 | 无法多轮修正（"再高一点"、"改荷载方向"） |
| 直接调用 LLM API，无上下文管理 | 用户问「为什么位移这么大」得不到解释 |
| 返回格式错误时仅提示 | 无自动修复/重试机制 |
| 不懂结构力学知识 | 生成的模型可能静定/超静定判断错误、约束不足 |

## 方案一：多轮交互式建模（P0，建议先做）

**核心思路**：把对话状态机化，支持「修改上一步结果」。

```
用户: 建一个3x3框架, 每层水平荷载10kN
  → LLM 生成模型 v1 → 应用+求解
用户: 改成2层, 荷载加到15kN
  → 携带 v1 模型 + 修改指令 → LLM 输出 v2 → 应用
```

实现要点：
1. **会话状态**：store 保存 `llmContext = { lastModel, lastResult, history[] }`
2. **提示词升级**：区分「新建」与「修改」两种意图（用 system prompt 引导 LLM 判断）
3. **结果对比**：v2 vs v1 差异高亮（画布闪动新节点/杆件）

工作量：前端为主，约 2-3 天。

## 方案二：求解结果解读（P1，教学价值最高）

**核心思路**：求解后让 LLM 解释结果，像助教一样。

```
用户: 帮我看看这个悬臂梁的弯矩图对不对
  → 前端把模型+结果(端力表)打包 → LLM 分析:
    "最大弯矩在固定端 M=45kN·m, 与理论值 PL=30×1.5=45kN·m 一致 ✔"
```

实现要点：
1. **结果打包器**：`buildResultContext(model, results)` 把关键数据压缩成 token 友好的文本
2. **模板化提问**：预设「验证/解释/比较」三类问题模板
3. **渲染**：LLM 回复支持简单 markdown（加粗、公式）

工作量：前端为主，约 2 天。

## 方案三：错误自修复（P2）

**核心思路**：LLM 输出 JSON 解析失败或求解失败时，自动带着错误信息重试一次。

```
LLM 输出 → JSON.parse 失败
  → 提取错误位置 → 追加提示"修正JSON格式" → 重试(最多2次)
求解失败(约束不足)
  → 把 femcli 错误信息回传 → LLM 补约束 → 重新应用
```

实现要点：
1. 重试循环（带最大次数+去重）
2. 错误信息 → 修复提示的 prompt 模板

## 方案四：结构力学教学教练（P3，愿景）

**核心思路**：不止生成模型，还教知识。

- **诊断模式**：`validateModel` 增强 + LLM 判断「这是什么结构类型？超静定几次？」
- **对比模式**：「简支梁 vs 连续梁，跨中弯矩差多少？」→ 自动建两个模型并排求解
- **问答模式**：「为什么这个桁架的斜杆受压？」→ 结合当前模型结果回答

## 技术选型建议

| 项 | 建议 |
|---|---|
| LLM 接口 | 维持 OpenAI 兼容（deepseek 等），不加依赖 |
| 上下文窗口 | 单次调用即可，无需 RAG |
| 输出格式 | 继续纯 JSON + 可选 markdown 解释字段 |
| 成本控制 | 模型上下文精简（模型 JSON 压缩为紧凑格式） |

## 推荐实施顺序

1. **方案一（多轮修改）**—— 解决"生成不对没法改"的最大痛点
2. **方案二（结果解读）**—— 教学场景直接加分
3. 方案三/四按需演进
